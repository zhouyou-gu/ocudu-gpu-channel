1 · 목적과 형태

이 통합이 무엇인가

이 작업 전에는 채널 에뮬레이터와 Sionna RT만 GPU에 있었고 gNB는 아니었다 — ZMQ로 IQ를 받아 PHY를 CPU에서 돌렸다. 이 통합은 gNB의 물리계층을 같은 GPU에 올려서 브로커 채널 → lower-PHY OFDM → PUSCH 등화·LDPC → LLR이 host를 오가는 연속이 아니라 하나의 device 상주 파이프라인이 되게 한다.

CUDA gNB는 선택 가능한 추가 프로파일이다. 고정된 CPU 빌드가 여전히 기준이자 회귀 방지망이고, 호출자가 명시적으로 켜지 않는 한 기존 게이트의 동작은 아무것도 바뀌지 않는다.

2 · 구성요소

무엇이 어디에 추가됐나

CUDA 관련은 전부 scripts/cuda/ 아래 신규 파일이다. 기존 게이트 스크립트는 환경변수 오버라이드 네 개를 받는 것 외에는 변경이 없고 (2개 파일 +67/−17), 산출물 검증기와 공유 워크스페이스 lock은 건드리지 않았다.

5 · 벤더 호환 패치

패치가 무엇을 바꾸고, 각 변경이 왜 필요한가

벤더 브랜치는 여기서 깨끗하게 빌드되지만, 자기 문서가 규정한 검증에서 12개 중 9개를 통과한다. 패치는 해시로 고정된 단일 파일이다 — 프로덕션 7파일 +88/−35, 테스트 4파일 +64/−13, SPDX 헤더 훼손 없음. 로컬에서 지고 가며 업스트림에 제보하고, 이 빌드에서 나온 모든 주장에 패치 적용 사실을 명시한다.

ID위치조건변경대조군
D1 srs_estimator_cuda_impl.cpp managed 격자만 구현하는 snapshot API를 강제 요구. 디스크리트 GPU는 pinned/host 격자로 도는데 거기서는 nullptr supports_device_grid_reading()으로 분기. managed는 벤더 경로 그대로, host/pinned만 기존 device grid reader로 스테이징 exit 8
D2 iq_compression_cuda.cpp host 소비자가 격자를 마이그레이션한 뒤 residency 게이트가 live read를 거부하는데, 호출자가 폴백 대신 false를 반환 벤더 자신의 주석이 명시한 owned snapshot 폴백을 구현하고, 잡았던 hold를 해제 exit 8
D3 factories.h · upper_phy_factories.cpp · pusch_demodulator_gpu_impl 가속 복조기 설정에 시간보간 필드가 없어서 CPU는 보간, GPU는 평균. 하드웨어와 무관 필드를 추가해 생성자까지 전달하고, 실제 적용된 모드를 로그로 남김 exit 8

D5 upper_phy_factories.cpp 가속 PDSCH가 codeblock executor를 요구하는데 ZMQ 순차 PHY는 의도적으로 주지 않음. 상호배타적이라 gNB가 구성 중 abort 가속 요청 + flexible 구성 + executor 부재일 때만 인라인 executor를 대입. 강제 CUDA PDSCH는 이미 동기 배치로 처리하므로 태스크 큐를 새로 만들지 않는다. 대입 사실을 로그로 남김 exit 2

원인축이 하나가 아니다

D1·D2는 디스크리트 GPU 조건이다 — 벤더는 통합 메모리에서 검증했고, 거기서는 격자가 항상 managed라 요구하는 API가 늘 존재한다. D3·D4는 하드웨어와 무관한 잠재 버그로 벤더 자기 플랫폼에서도 재현된다. D5는 둘 다 아니고, gNB를 ZMQ 라디오로 구동하는 데서 오는 성질이다.

벤더 테스트가 D3·D4를 못 보는 이유

pusch_gpu_cpu_comparison_test가 양쪽을 average 보간으로 고정하고, CFO를 0으로 두고, deferred 경로만 탄다. 추가한 회귀는 정확히 그 셋을 바꾼다 — 서로 다른 설정, 0이 아닌 CFO, 동기 경로. 게다가 D3은 고치기 전에는 테스트 자체를 쓸 수 없다. GPU에 다른 전략을 요구하려면 부재 자체가 결함인 그 필드가 필요하기 때문이다.

심각도 — D3

기본 gNB 설정 + 0이 아닌 CFO에서 CPU 기준은 BLER 0 %, GPU 경로는 100 %, 디코드 일치율 0 %다. 여기서는 라이브 실패로 드러났다 — attach는 성공한 뒤 PDU 세션 수립이 PUSCH CRC 165 KO / 1 OK로 실패했다.

8 · 알려진 제약

하향 격자는 device에 머무를 수 없다

Lower-PHY TX는 하향 격자를 device에서 직접 읽지 않고 host에 staging한 사본을 읽는다. 여전히 CUDA이며, 패치로 고칠 수 없다 — 직접 리더는 managed 메모리 coherence 속성 세 개를 모두 요구하는데 이 GPU는 하나만 만족한다.

완전 coherent가 아니면 하향 격자에 대한 모든 host 쓰기가 페이지를 host로 마이그레이션하고 device residency를 해제한다. PDCCH와 SSB는 이 브랜치에서 가속 대상이 아니라 CPU가 매 슬롯 같은 격자에 쓴다 — PDSCH가 격자를 device 상주로 만들면, 제어 채널이 그것을 host로 끌어오고, 변조기의 device 읽기가 거부된다. directManagedAccessFromHost = 0은 CPU가 GPU 상주 managed 페이지를 마이그레이션 없이 건드릴 수 없다는 뜻이므로, 유일하게 올바른 해법은 CPU 생성 채널을 별도 버퍼에 쓰고 device에서 병합하는 것 — 모든 하향 채널 처리기가 쓰는 writer 인터페이스를 다시 쓰는 일이지 호환 패치가 아니다.

업스트림에는 결함이 아니라 문서에 대한 관찰로 제보한다. 문서는 옆의 PDSCH 선택자에 대해서는 디스크리트 동작을 명시하면서 low_phy_tx_acceleration_mode에는 이 구분을 적지 않았다. 이 fixture에서 staging 비용은 슬롯당 약 70 KB다.
